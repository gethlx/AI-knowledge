# 复审结论

**仍需修订。**

v2.2 已实质修复 F-01、F-05、F-06、F-09、F-10、F-11、F-12、F-13 的主要问题，P7.5 也已从概念性要求提升为较完整的任务规格。但当前版本仍有三个阻塞点：

1. **§2.5 的 `waived_by_owner` 仍可绕过 blocking 关闭规则**，与同节“blocking 只能两条路关闭”的表述直接矛盾。
2. **§2.5 的 light 排除机制虽然不再冒充 `REJECTED_MODEL_ADJUDICATED`，但仍未与 14 号要求的 P5“候选均有证据和模型意见”完全衔接**。它解决了状态伪造问题，但没有解决正式候选覆盖问题。
3. **§4.2 的 P7.5 容量与失败恢复规格仍不够闭合**：只规定了 12 万字符阈值和压缩方向，没有规定最终可提交上限、分块后的全图审查如何合并，也与 14 号 §8.5 的通用 sol 超时/退避协议产生未授权差异。

此外，§2.2 的接力协议虽然具备原子落盘和基本抢占逻辑，但没有给出真正的租约、过期、崩溃恢复和盲评隔离机制，仍不足以称为可直接执行的并发协议。

因此不能批准 v2.2 直接生效。修复上述 blocking 后，可以进入执行。

# 重点审查

## 1. §2.5 台账终态是否闭合

**记账层面基本闭合，执行语义没有完全闭合。**

好的部分：

- 4,051 对逐行记账；
- 每对要求唯一终态；
- full/light 数量可核对；
- `LIGHT_SILENT_EXCLUDED` 不冒用拒绝裁定；
- 报告按候选对总数统计，而不是只报告意见文件数。

问题在于，这三个终态的含义不对称：

```text
FULL_REVIEWED
LIGHT_DISPUTED -> FULL_REVIEWED
LIGHT_SILENT_EXCLUDED
```

前两个终态最终会进入 P6，第三个终态不会进入正式图。于是 P5 实际上不是“全量候选送审并完成模型复核”，而是：

- 1,769 对进行完整三路复核；
- 2,282 对经过某种例外式筛选后被排除。

这可能是一个合理的范围控制方案，但它与 14 号 §四中 P5 的“全量候选生成与多模型复核”“候选均有证据和模型意见”不完全一致。v2.2 没有明确写出：

- light 对是否属于正式候选；
- 若属于，14 号 P5 规则为何允许其不取得三路意见；
- 若不属于，谁在何时把它们从正式候选池降为“仅供召回/排除审计”的对象；
- light 排除是否需要人工或 sol 批准；
- 后续新增规则、模型或卡文变化时，这些排除对是否必须重新评估。

因此，§2.5 需要在 14 号总纲下补一个明确的范围裁定。不能只靠“不得进入正式图”解决所有覆盖问题。

## 2. §2.2 接力协议是否可操作

**具备文件完整性保护，但尚未形成可靠的任务领取协议。**

已具备：

- 临时文件；
- 原子重命名；
- 完成文件不覆盖；
- 缺失槽位续跑；
- 接力日志；
- U6 体量测量和切分预案。

不足：

1. “领取互斥”没有实际锁、租约或原子 claim 文件。  
   两个会话可以同时读取“目标不存在”，随后同时调用模型。最终可能只有一个文件落盘，但两次调用都已经产生费用。

2. 没有租约过期规则。  
   某会话领取任务后死亡，后续会话无法区分“正在处理”还是“已经遗弃”。

3. 没有定义失败槽位状态。  
   `*.tmp` 是未完成、失败、超时还是可重试，当前没有明确 Schema。

4. 没有把盲评隔离落实到接力上下文。  
   14 号要求三路模型互相不可见。§2.2 的“单元共享同一份输入上下文”和“会话接力”没有明确说明：每条 reviewer 路由是否使用独立工作目录、独立上下文、独立输入队列，接力会话是否绝不携带其他 reviewer 的响应。

因此，§2.2 当前可支持低并发的人工操作，但不能作为高可靠编排器的完整执行协议。

## 3. §4.2 是否覆盖 F-04 全部要求

**覆盖了审计和失败状态的大部分要求，但没有解决容量和分块执行的核心歧义。**

已经覆盖：

- 独立任务接口；
- 幂等键；
- 输入哈希；
- 实际体量测量；
- 禁止静默截断；
- 非法输出失败；
- finding 引用完整性校验；
- 重试；
- `P75_FAILED`；
- 同一图版本完整重跑；
- 失败阻塞 P8。

仍未覆盖：

- “12 万字符”究竟是警戒线、提交上限还是压缩触发线；
- 压缩后仍超限时的确定性处理；
- 分块方案是否允许；
- 如果允许，如何合并 findings；
- 分块是否能发现跨社区、跨块的全局拓扑问题；
- 哪一个结果代表“全图审查完成”；
- P7.5 是否必须由 sol 一次性读取完整正式图。

当前文字同时出现：

- “P7.5 是全图整体审查”；
- “sol 单次调用”；
- “超 12 万字符时改分块方案”。

这三项不能并列存在而不定义分块语义。必须二选一：

- 要求真正单次全图审查，则应给出可验证的压缩算法和最终输入上限，超限直接 `P75_FAILED`；
- 允许分块，则必须定义全局摘要、块间关系审查、findings 合并、覆盖证明和最终聚合裁定，不能继续称为单次全图审查。

## 4. §4.4 blocking 规则是否可被绕过

**可以。**

直接矛盾如下：

§4.4 说：

> blocking 关闭仅两条路：① 有记录的修复 + 受影响边经 14 号流程重审通过 + 重建图版本 + 复审通过；② 升级 `ESCALATE_HUMAN` 由主公裁决。

但同一节又说：

> 发布闸门：存在未处置（open）的 blocking → P8 不得执行；处置选项：等待修复 / 发布延期 / 经主公批准缩小发布范围。

§4.3 Schema 允许：

```text
disposition_status:
open | fixed | escalated | waived_by_owner
```

§五又规定：

```text
无 open 状态 blocking
fixed/escalated/waived_by_owner 方可放行
```

这等于增加了第三条关闭路径：

```text
waived_by_owner
```

而且没有规定：

- owner 是否必须是主公；
- 是否必须有主公批准记录；
- 是否必须排除受影响边；
- 是否必须重建图；
- 是否必须对缩小范围后的图重新执行 P7 和 P7.5；
- waiver 是否只表示暂缓处置，还是允许正式发布。

这不是文字小瑕疵，而是会直接改变 P7.5 发布闸门的行为。必须删除 `waived_by_owner`，或者把它严格改为：

```text
waived_by_owner = 仅表示主公明确批准的范围性豁免
```

并强制附带：

- `human_decision_id`；
- 主公批准时间；
- 被豁免的具体 edge/node；
- 排除后的新 `graph_version`；
- 新图 P7 机械校验通过；
- 新图 P7.5 完整复审通过；
- 发布范围声明和回滚目标。

# 新发现问题

## N-01｜blocking｜`waived_by_owner` 绕过 blocking 发布闸门

这是上文 F-03 遗留问题的具体化，也是 v2.2 自身引入的条款冲突。

**依据：**

- §4.3 允许 `waived_by_owner`；
- §4.4 声称 blocking 只有“修复重审”或“升级主公”两条路；
- §五把 `waived_by_owner` 与 `fixed/escalated` 并列为可放行状态。

**风险：**

任意 owner 可能通过改变 `disposition_status` 使 P8 通过，而没有边级重审或主公明确批准记录。

**必须修复：**

删除 `waived_by_owner`，或将其限定为主公批准的范围缩小发布，并强制重建和复审新图。否则 v2.2 不可执行。

## N-02｜blocking｜P7.5 超限后的“压缩/分块”路径不闭合

**依据：**

- §4.2 规定输入超过 12 万字符时压缩边理由摘要；
- 仍超限时“改分块方案并记录”；
- 同节又规定“sol 单次调用”。

**风险：**

分块后的输出可能无法发现跨块的全局问题；不同执行者可以采用不同分块方法，导致不可复现；也无法判断何时算完成整体审查。

**必须修复：**

明确采用单次压缩审查还是分块审查。若采用分块，必须补充分块算法、全局摘要、跨块审查、结果聚合和覆盖证明。

## N-03｜blocking｜P7.5 超时和退避协议未经 14 号 §8.5 授权衔接

**依据：**

- 14 号 §8.5：单次 120 秒，重试间隔 30 秒、60 秒；
- v2.2 §4.2：P7.5 单次 300 秒，重试 3 次，间隔 0/60/120 秒，并称为“8.5 协议的图级任务特化版”。

**风险：**

14 号明确要求所有 sol 调用遵守 8.5 协议。v2.2 不能仅通过自称“特化版”改变超时和退避规则，否则执行器无法判断哪个规则优先，也会出现同一 sol 调用类别使用不同稳定性协议的问题。

**必须修复：**

在 14 号总纲中新增明确授权，或将 P7.5 的参数写成 8.5 的正式例外协议，并说明：

- 300 秒是否覆盖单次 subagent 调用总时长；
- 重试次数是否仍为 3；
- P7.5 是否进入 `ADJUDICATION_DEFERRED`，还是使用独立 `P75_FAILED`；
- 熔断阈值是否适用；
- 每次重试是否复用同一幂等键且不重复计费。

## N-04｜suggestion｜接力协议没有实现 reviewer 级盲评隔离

**依据：**

- 14 号 §3.2 要求三路评审互相不可见；
- §2.2 允许单元共享输入上下文，并通过会话接力处理缺失槽位；
- §七只要求保存单元文件和日志，没有说明 reviewer 级上下文隔离。

**风险：**

如果接力会话读取单元目录中的既有 reviewer 文件、汇总状态或错误日志，就可能把其他模型的结论、失败原因或排序信息带入下一路请求，污染独立性。

**建议修复：**

为每个 `unit_id + reviewer_id + relay_attempt` 建立独立输入和工作目录；模型调用前只能读取冻结卡文、规则、Schema 和该 reviewer 自己的任务状态；禁止读取其他 reviewer 文件、汇总结果及裁定队列。把隔离校验记录入 `relay_log`。

## N-05｜suggestion｜`LIGHT_SILENT_EXCLUDED` 缺少后续重评估触发条件

**依据：**

- §2.5 将静默 light 对排除出正式图；
- §2.1 将 4,051 对作为冻结候选池；
- §六声称按当前候选池完成 P5。

**风险：**

排除状态可能被长期保留，即使后续准则、卡文、召回模型或社区结构变化，原本的 light 对已经具备正式审查价值。

**建议修复：**

为 `LIGHT_SILENT_EXCLUDED` 记录排除所依据的：

- 候选池版本；
- 规则版本；
- 卡文哈希；
- 召回版本；
- 排除机制版本。

当上述任一项变化时，强制重新评估，不得直接继承排除状态。

## N-06｜informational｜P7.5 findings Schema 的顶层结构不明确

**依据：**

§4.2 要求结构化 findings，§4.3 展示的 JSON 更像单条 finding 对象，但没有定义完整输出是数组、包络对象还是逐条文件。

**风险：**

不同实现可能输出：

```json
[ {...}, {...} ]
```

或：

```json
{ "findings": [ ... ] }
```

`p75_id`、`graph_version`、`review_input_hash` 的重复和总数校验方式也会不同。

**建议修复：**

定义固定顶层结构，例如：

```json
{
  "p75_id": "...",
  "graph_version": "...",
  "review_input_hash": "...",
  "findings_total": 0,
  "findings": []
}
```

并规定 `findings_total` 必须等于数组长度。

# 最终裁定

**结论：仍需修订。**

v2.2 不是不可执行的方向性草案，且已经完成了大量有效修订；但不能按当前版本直接替代 14 号的 P5/P7 执行细则。
