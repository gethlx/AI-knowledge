## 一、最终结论

原规划的总体工程骨架可保留，但必须更换“可信边”的定义和裁决机制。

最终采用以下链路：

> **冻结 197 个节点与卡文 → 候选召回 → 多模型独立提议 → 交叉审查与分歧分析 → 主模型最终裁定 → 安全/阻塞红线审查 → 版本化图谱发布 → LightRAG 作为检索承载层。**

本项目不再以“人工逐对裁决”作为默认路径，也不再把模型裁定结果称为“人工确认边”或“客观可信边”。

正式状态分为：

| 状态 | 含义 | 是否可进入学习路径/课程编排 |
|---|---|---:|
| `SOURCE_TRUSTED` | 真源卡文，当前唯一事实来源 | 能 |
| `PROPOSED_UNVERIFIED` | 单模型或单轮模型提议 | 不能 |
| `AI_REVIEWED` | 至少两条独立模型意见已交叉审查 | 不能单独进入 |
| `ACCEPTED_MODEL_ADJUDICATED` | 多模型证据一致，主模型完成最终裁定，未触发红线 | **能，但必须标注“模型裁定，未人工逐条核验”** |
| `ESCALATE_HUMAN` | 安全、阻塞、严重冲突或证据不足 | 不能，等待主公处理 |
| `REJECTED_MODEL_ADJUDICATED` | 模型互审后判定无关系或不满足证据要求 | 不能 |
| `DERIVED_TRANSITIVE` | 根据已裁定先修边推导的传递关系 | 默认不能作为直连边；仅作可达性辅助 |

“模型裁定可用”不等于“人工核验可信”。发布物必须同时显示裁定方式和残余风险。

## 二、三项阻塞性问题及裁定修正

### 阻塞 1：原规划的人工裁决流程与用户决策冲突

原规划第 P3、P4、P6 以及第 11 节均要求主公或人工逐对裁决，估算 500–850 对、5–14 小时。这与最新决策冲突，不能继续作为执行前提。

**直接修正：**

- 删除“主裁决人保持单一”“主公亲自裁决 500–850 对”等执行要求；
- P3 的 K1 全 190 对不再由人工逐对裁决，而由多模型对 190 对全量生成独立判断；
- 主模型对分歧进行最终裁定；
- 仅 `ESCALATE_HUMAN` 队列上报主公；
- 人工投入从“默认全量”改为“重大安全/阻塞性问题的例外处理”。

### 阻塞 2：模型裁定结果不能继续使用 `ACCEPTED_HUMAN`

原规划把“模型互审 + 主模型裁定”仍塞进 `ACCEPTED_HUMAN`，会让下游误认为已经人工确认。这是可信度标记错误，必须阻断。

**直接修正：**

- 新增 `ACCEPTED_MODEL_ADJUDICATED`；
- `ACCEPTED_HUMAN` 仅为兼容历史 schema 保留，不得由当前流程生成；
- 可信边文件改名为 `accepted_model_adjudicated_edges.jsonl`，避免伪装成人工金标准；
- 所有图谱顶部和 release manifest 必须写明：模型裁定、未人工逐条核验；
- `ESCALATE_HUMAN` 不得进入正式图、学习路径和课程编排。

### 阻塞 3：LightRAG 图与正式关系图不能要求计数一致

当前 `run_lightrag.py` 的 LightRAG 抽取图来自文档摄入期间的实体/关系抽取；它与后续独立的模型建边结果不是同一数据集。当前脚本也没有一个稳定、已验证的公开关系导入 API，不能假设“把正式边写回 LightRAG 私有存储”后四处边数天然一致。

**直接修正：**

- 正式知识图谱的唯一关系真源改为 `accepted_model_adjudicated_edges.jsonl`；
- `graph.json`、GraphML、HTML 从该真源生成；
- LightRAG 只承担文本块、向量检索和问答上下文承载；
- LightRAG 自动抽出的关系只存为 `lightrag_extracted_edges_unverified.jsonl`，不得并入正式关系图；
- P7 的验收从“LightRAG、JSON、GraphML、HTML 四处计数一致”改为：
  - 正式 JSON、GraphML、HTML 三处节点/边/edge_id 一致；
  - LightRAG 节点索引与 197 张卡一致；
  - LightRAG 非正式关系与正式边集分开计数、分开标记；
  - 两者不再要求边数相等。

## 三、模型互审机制（替代人工裁决）

### 3.1 模型角色（2026-09-26 调整：主控换防，sol 降为按需裁定建议）

每个候选概念对必须经过三份**独立评审意见**。三名评审模型来自不同模型来源，互相不可见：

1. **评审模型 A：** `glm5.3-flash`；
2. **评审模型 B：** `deepseek4.1flash`；
3. **评审模型 C：** `hy4`；
4. **编排主控：** **当前会话模型（`glm5.3-flash` 编排层）**——只推动流程，不裁边；
5. **综合裁定建议模型：** `gpt-5.6-sol`——**按需经 subagent 拉起**，仅在需要综合裁决时调用。

**主控换防原因：** `gpt-5.6-sol` 近期不稳定，不能作为常驻主控（否则主控一卡，全流程死锁）。改为：日常编排、pair 分发、程序校验、结果落盘全部由当前会话模型（glm5.3-flash 编排层）驱动；sol 只在被拉起时给出**裁定建议**，主控采纳后执行落盘。

职责划分：

**编排主控（当前会话模型）负责：**

- 启动和推动整个任务流程；
- 生成 pair 任务、分发三路评审请求、收集结果；
- 程序化校验（Schema、实体、逐字证据、禁用字段）；
- 按需经 subagent 拉起 `gpt-5.6-sol` 获取裁定建议，采纳后执行落盘；
- 维护任务状态、失败重试、成本和版本记录；
- 将必须人工处理的事项写入 `ESCALATE_HUMAN` 队列。

**`gpt-5.6-sol`（经 subagent 按需拉起）只负责：**

- 读取 review_bundle + 原始卡文；
- 对普通分歧给出裁定建议；
- 识别安全、阻塞、证据不足和系统性漂移；
- 输出裁定建议、理由、残余风险和是否升级。

**独立性红线：** 编排主控是三路评审之一（评审 A），**绝对不得在 sol 不可用时自己补裁定**——评审员自己当法官，互审作废。sol 不可用的 pair 一律进 `ADJUDICATION_DEFERRED` 队列，待 sol 恢复后补裁；流水线继续推进其他 pair，不得整体卡死。

禁止把 sol 的裁定建议伪装成第四个独立评审意见。禁止用同一模型的不同温度、不同提示词或不同别名冒充不同来源模型。若任一路评审模型不可用，该 pair 必须标记为 `REVIEW_INCOMPLETE`，不得用任何方式补齐缺失意见后宣称完成互审。

### 3.2 互审输入隔离与独立性证明

- `glm5.3-flash`、`deepseek4.1flash`、`hy4` 三路评审并行启动；任何一路不得看到其他路的请求内容、答案、置信度、排序或失败原因；
- 三路评审收到完全相同的卡文快照、pair_id、关系定义和输出 Schema；不得给某一路额外提示；
- `gpt-5.6-sol` 只在三路结果收齐或超时后读取汇总包，不参与盲评；
- 任何模型都不能读取 `04_归档/前置后续-作废字段归档.csv`；
- 每个模型的输出保留原始响应、模型请求名、API 返回名、来源标识、Prompt 版本、输入卡文哈希、时间戳和请求状态；
- 评审请求必须使用不同的 `reviewer_id`，但 `reviewer_id` 不是独立性的证明；独立性证据以不同模型来源 + 输入隔离日志为准；
- 所有 `evidence.quote` 做逐字子串校验，校验失败的意见自动降级为无效意见；
- 三路输出不得在模型调用前做任何聚合、排序或前置结论注入；
- 如果同一模型来源被路由层实际返回为另一个别名，必须记录请求名和返回名，并将该路独立性标记为 `ROUTING_ALIAS`，不能仅凭请求名宣称来源不同。

### 3.3 最终裁定规则

三路评审的可接受结果先经编排主控做程序化校验，再由主控经 subagent 拉起 `gpt-5.6-sol` 获取裁定建议；主控采纳建议后落盘。sol 建议不能跳过缺失意见，也不能把自己的判断当成独立票；主控不得在 sol 缺席时自行裁定（独立性红线，见 3.1）。

| 三路评审结果 | sol 裁定建议（主控采纳后执行） |
|---|---|
| 三路一致为同一方向/类型，证据均逐字命中，且证据足以支持关系、无 DAG 冲突 | `ACCEPTED_MODEL_ADJUDICATED` |
| 两路一致、一路明确反对 | `ESCALATE_HUMAN`；sol 必须记录反对理由，不能简单多数放行 |
| 两路一致、一路 `INSUFFICIENT_EVIDENCE`，支持意见证据充分且无红线 | sol 可裁定 `ACCEPTED_MODEL_ADJUDICATED`，但必须标注 `minority_uncertain` |
| 三路一致为 `RELATED`，证据充分且不涉及先修方向 | `ACCEPTED_MODEL_ADJUDICATED`，关系层为 related |
| 三路一致为 `NO_RELATION`，且没有有效证据支持关系 | `REJECTED_MODEL_ADJUDICATED` |
| 任意一路发现卡文矛盾、证据不成立或关系方向有实质反例 | `ESCALATE_HUMAN` |
| 方向冲突、关系类型冲突、评审路由异常或评审缺失 | `REVIEW_INCOMPLETE` 或 `ESCALATE_HUMAN` |
| 出现安全、伦理、医疗、法律、未成年人风险或课程阻塞性错误 | `ESCALATE_HUMAN` |
| 触发先修环、双向边、严重拓扑冲突 | `ESCALATE_HUMAN`，不得自动删旧边或强行放行 |

其中：

- `REVIEW_INCOMPLETE` 表示互审尚未完成，不能进入正式图；
- `ADJUDICATION_DEFERRED` 表示三路评审完成但 sol 裁定建议未能获得（不可用/超时/重试耗尽），挂起等待补裁，不能进入正式图；
- `ESCALATE_HUMAN` 表示已完成模型审查但超出自动裁定边界，必须上报主公；
- “三路一致”也只表示模型来源之间一致，不表示客观真理；
- 核心课程入口、关键学习路径、会改变拓扑主干的关系，默认按高影响项处理：即使三路一致，也由 sol 复核后决定是否升级，不得仅凭多数票放行。

正式报告必须报告：三路一致率、二对一分歧率、证据通过率、路由异常率、`REVIEW_INCOMPLETE` 数量、`ADJUDICATION_DEFERRED` 数量、`ESCALATE_HUMAN` 数量、最终接受率和拒绝率。

### 3.4 K1 不再叫“人工金标准”

原 `k1_gold_decisions.jsonl` 改为：

- `k1_multi_model_adjudications.jsonl`
- `k1_disagreement_cases.jsonl`
- `k1_escalation_queue.jsonl`
- `k1_model_adjudication_metrics.json`

K1 的作用从“建立人工金标准”改为：

- 测量多模型之间的一致性；
- 测量证据引用是否可靠；
- 测量最终裁定是否稳定；
- 找出必须上报主公的安全和阻塞案例；
- 评估候选召回，而不是宣称建立客观真值。

原规划的 Recall@5、候选证据命中率、表外实体数、先修环检测仍保留；“与人工金标准比较的准确率”删除。

## 五、物理AI增量升级最终口径

第十一节保留，但其中“人工裁决”全部替换为“glm5.3-flash + deepseek4.1flash + hy4 三路独立互审 + 主控采纳 gpt-5.6-sol 裁定建议（按需拉起）+ 红线升级”。

新增“物理AI”时：

1. 以当前已发布版本为只读基线；
2. 新卡经过字段完整性、名称冲突和卡号唯一性检查；
3. 只生成“新卡 × 旧卡”以及“新卡 × 新卡”的候选对；
4. 使用与基线相同的三路召回和互审配置；
5. 新增边先为 `PROPOSED_UNVERIFIED`，再经 `AI_REVIEWED` 和 `ACCEPTED_MODEL_ADJUDICATED`；
6. 任何环、方向冲突、卡文不足或安全问题进入 `ESCALATE_HUMAN`；
7. 基线 `G_v1` 不变，形成独立 delta 包；
8. 全图重新跑节点、边、环、证据、状态、检索回归；
9. 通过后切换发布指针，失败则回滚到 `G_v1`。

不得因新增节点而重跑旧节点之间的全部候选对；只有旧卡内容、准则、召回模型或关系语义发生变化时，才触发规定范围的重评估。

| **综合裁定建议** | **`gpt-5.6-sol`** | 已有自定义模型配置，**经 subagent 按需拉起** | 分歧综合分析、裁定建议、残余风险评估；**不可用时不阻塞流水线** |
| LightRAG 摄入抽取 | `gpt-5.6-luna` | 已完成的 LightRAG 选型（11 号报告） | 仅文本摄入抽取，不参与三路独立互审 |
| **LightRAG 查询** | **`gpt-5.6-sol`** | **已完成的 LightRAG 选型（11 号报告）** | **检索后的答案生成，消化长噪声上下文** |
| 向量 | `glm-embedding-3-pro` | 已完成的 LightRAG 选型（11 号报告） | 节点检索和候选召回 |

**LightRAG 三件套口径（11 号报告定案，本轮只执行不重选）：** 抽取=`gpt-5.6-luna`，查询=`gpt-5.6-sol`，向量=`glm-embedding-3-pro`（4096 维）。`run_lightrag.py` 的 `LIGHTRAG_MODEL=gpt-5.6-luna` 只管摄入抽取；查询阶段必须显式指定 sol，不得沿用 luna。

**模型来源口径必须分开：** `glm5.3-flash`、`deepseek4.1flash`、`hy4` 是 WorkBuddy 内置模型，不从 `~/.workbuddy/models.json` 判断，也不需要写入该自定义模型配置文件。`gpt-5.6-sol` 属于已配置的自定义模型，通过 subagent 按需调用。

### 8.2 重要边界

1. `glm5.3-flash` 与 `glm-embedding-3-pro` 不是同一角色：前者是 WorkBuddy 内置的独立关系评审模型，后者是已经确定的 LightRAG 向量模型。
2. `gpt-5.6-luna` 与 `glm-embedding-3-pro` 的 LightRAG 角色已由前序模型选型报告确定，本轮只执行，不重新评估、替换或扩展模型组合。**三路 WorkBuddy 内置评审模型不属于 LightRAG 模型组合，不能拿二者互相替换。**
3. `gpt-5.6-luna` 不参与关系互审；它只服务于 LightRAG 摄入抽取，且其产出的关系仍然是未核验关系。
4. `gpt-5.6-sol` 不参与三路盲评，否则会破坏评审模型和裁定建议模型的职责隔离。
5. 三路内置模型的调用由 WorkBuddy 子代理调度层负责，不通过 `~/.workbuddy/models.json` 配置；审计记录仍需保存评审模型标识、Prompt 版本、输入卡文哈希和时间戳。
6. 如果任一内置评审模型无法在当前 WorkBuddy 会话中被调度，不能用其他模型顶替并宣称互审完成；该批次必须进入 `REVIEW_INCOMPLETE`，由编排主控报告阻塞原因。
7. 当前执行规划不重新验证或调整 LightRAG 的模型组合；LightRAG 三件套按 11 号选型报告冻结：抽取 `gpt-5.6-luna`、**查询 `gpt-5.6-sol`**、向量 `glm-embedding-3-pro`（4096 维）。三路内置模型只用于关系评审。
8. **编排主控不得在 sol 不可用时自行裁定**（主控本身是评审 A，自裁即独立性污染）；只能标记 `ADJUDICATION_DEFERRED` 挂起补裁。

### 8.3 推荐的编排调用顺序

```text
P0 读取并冻结 card_evidence.jsonl（编排主控执行）
  ↓
P1 生成 pair_id 和统一评审输入
  ↓
并行调用 glm5.3-flash / deepseek4.1flash / hy4
  ↓
编排主控程序校验 JSON、规范实体、逐字证据、禁用字段、路由状态
  ↓
汇总为 review_bundle.json
  ↓
编排主控经 subagent 拉起 gpt-5.6-sol 读取 review_bundle + 原始卡文
（超时/失败走 8.5 稳定性协议，不得卡死流水线）
  ↓
输出裁定建议 → 编排主控采纳并落盘
  ↓
执行 DAG / 安全 / 阻塞校验
  ↓

```

### 8.4 P1 最低可运行接口

P1 阶段必须真正落地以下接口，而不是只写在报告里：

- `reviewer_glm(prompt) -> ReviewOpinion`（由 WorkBuddy 内置模型子代理执行）
- `reviewer_deepseek(prompt) -> ReviewOpinion`（由 WorkBuddy 内置模型子代理执行）
- `reviewer_hy4(prompt) -> ReviewOpinion`（由 WorkBuddy 内置模型子代理执行）
- `sol_adjudicate(card_pair, review_bundle) -> Adjudication`（编排主控经 subagent 按需拉起 `gpt-5.6-sol`，受 8.5 稳定性协议约束）
- `validate_opinion(opinion, card_evidence) -> ValidationResult`
- `route_adjudication(adjudication, graph_state) -> FinalStatus`

每条 `ReviewOpinion` 至少包含：

```json
{
  "pair_id": "1-01__1-02",
  "reviewer_id": "reviewer_glm|reviewer_deepseek|reviewer_hy4",
  "model_requested": "...",
  "model_returned": "...",
  "relation_type": "prerequisite|related|no_relation|insufficient_evidence",
  "direction": "source_to_target|target_to_source|null",
  "evidence": [],
  "reason": "仅解释卡文如何支持判断",

  "input_card_hash": "...",
```

`sol_adjudicate` 不得只取多数票，必须对少数意见、证据命中、关系影响范围和红线结果逐项复核，并产出可追溯的裁定理由。

### 8.5 gpt-5.6-sol 调用稳定性协议（2026-09-26 新增）

sol 近期不稳定，所有对 sol 的调用必须遵守以下协议，任何情况下不得让流水线卡死：

```text
调用 sol（经 subagent）
  ├─ 正常返回 → 采纳裁定建议，落盘
  ├─ 超时（单次 120s）→ 重试
  │     ├─ 第 2 次（间隔 30s）
  │     ├─ 第 3 次（间隔 60s）
  │     └─ 3 次全失败 → 该 pair 标记 ADJUDICATION_DEFERRED，写入 deferred_queue.jsonl
  │                        流水线跳过该 pair，继续处理后续
  └─ 返回内容非法（非 JSON/Schema 不合）→ 视同失败，计入重试
```

规则：

1. **重试上限 3 次**，指数退避（0s / 30s / 60s）；每次重试记录时间戳和失败原因；
2. **deferred 队列幂等**：sol 恢复后可对 `deferred_queue.jsonl` 补跑，缓存键不变，不重复计费；
3. **禁止主控自行裁定**：主控（评审 A）不得在 sol 缺席时补裁，否则互审独立性作废；deferred 就是挂起，不是放行；
4. **批量故障熔断**：连续 10 个 pair 进入 deferred，暂停 P3/P6 裁定阶段，编排主控向主公报告 sol 故障，等待指令；已完成的评审数据保留不丢；
5. **与 REVIEW_INCOMPLETE 区分**：`REVIEW_INCOMPLETE` 是三路评审缺员；`ADJUDICATION_DEFERRED` 是三路齐但裁定建议未获得——两者都不得进入正式图；
6. sol 恢复的判定：补跑 deferred 队列首个 pair 成功且 Schema 校验通过，即视为恢复，继续批量补裁。
