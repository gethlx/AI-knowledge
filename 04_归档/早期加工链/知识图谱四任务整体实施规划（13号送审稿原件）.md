## 一、结论

四项任务不能按“让 LightRAG 自动抽边 → 直接出图”的思路推进。正确实施链只有一条：

> **冻结可信节点与卡文 → 制定标注准则 → AI 提议候选边 → K1 全量对照验证 → 人工裁决 → 逻辑推断与冲突检查 → 可信边入库 → LightRAG 合并与图谱交付。**

LightRAG 的职责限定为：

1. 197 张卡的节点索引；
2. 向量检索与问答承载；
3. 接收已经人工裁决的可信边；
4. 导出图谱与可视化数据。

LightRAG **不是可信建边器**。任何模型自动生成的关系，在人工裁决前都只能进入候选区，不能进入可信图、学习路径、拓扑分层、推荐系统或课程决策。

## 二、四类数据的使用权限

| 数据层 | 状态 | 能不能用 | 允许用途 | 禁止用途 |
|---|---|---:|---|---|
| 197 张规范卡 | `SOURCE_TRUSTED` | **能用** | 节点、实体对齐、卡文证据、候选生成、检索 | 不得篡改卡号和规范名 |
| AI 候选边 | `PROPOSED_UNVERIFIED` | **不能用于决策** | 排队、人工裁决、模型评测 | 学习路径、拓扑、CIS、课程编排、正式图谱 |
| 人工裁决直连边 | `ACCEPTED_HUMAN` | **能用** | 可信图、路径、拓扑、查询、可视化 | 不得省略裁决人与证据 |
| 传递推断边 | `DERIVED_TRANSITIVE` | **有限可用** | 可达性判断、减少重复裁决、冲突检测 | 不得伪装成人工逐条确认；默认不写入基础直连边集 |
| 被拒绝概念对 | `REJECTED_HUMAN` | **能用于排除** | 防止模型反复提议、错例分析 | 不得进入图谱 |
| 对称相关边 | `RELATED_HUMAN` | **能用** | 对照、易混、延伸关系展示 | 不得进入先修 DAG 或拓扑排序 |

**硬规则：先修图和相关图必须分层存储。** “相关”可以成环；“先修”必须为 DAG。两者混在一张边表里跑拓扑，必然把图做烂。

## 四、P0：基线冻结与开工检查

### 4.1 工作内容

1. 从 v3.9.6 真源解析 197 张卡，生成唯一的规范实体注册表。
2. 只提取可信字段：卡号、中文名、知识标签、学习场景、认知层级、精确定义、常见误解、典型案例、反例、深度上限、安全与伦理边界、来源依据、教学类比。
3. 对所有输入目录做禁用字段扫描，确认归档旧字段没有进入候选生成输入。
4. 固定运行模型、端点、embedding 维度、Prompt 版本、随机参数与代码版本。
5. 修复配置漂移后再启动 K1：当前 `run_lightrag.py` 文档说明写的是 Vimox Router + `gpt-5.6-luna` + `glm-embedding-3-pro`，但代码第 36–38 行默认值仍是旧端点、`gpt-5.4`、`text-embedding-3-small`。这属于阻断性问题。

### 4.2 产出物

- `canonical_entities.json`：197 个规范实体，键为卡号，值含唯一规范名。
- `card_evidence.jsonl`：每卡一行，仅含允许用于证据的卡文字段。
- `source_manifest.json`：输入文件哈希、卡数、字段白名单、生成时间。
- `runtime_manifest.json`：端点、抽取模型、查询模型、embedding 模型和维度、代码版本、Prompt 版本。
- `preflight_report.md`：禁用字段扫描、实体唯一性、卡数、配置一致性检查结果。

### 4.3 验收标准

- 卡数恰为 197；卡号唯一 197/197；规范名唯一 197/197。
- 每个实体名严格为“卡号 中文名”；不存在简称、英文名或无卡号实体。
- 候选生成输入中，归档旧边值命中数为 0。
- 字段白名单之外的内容不得进入 `card_evidence.jsonl`。
- 模型与端点实际运行值和交接简报一致；不得只看注释或环境变量说明。
- embedding 返回维度实测为 4096，且所有向量写入前维度一致。

### 4.4 风险点

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 旧字段从归档、旧 JSON 或缓存中回流 | 候选被历史错误锚定 | 输入白名单 + 路径白名单 + 全文扫描；旧归档不挂载到运行目录 |
| 脚本文档和实际默认值不一致 | K1 结论无效、成本和质量失真 | 运行前打印并保存 effective config；不匹配即失败退出 |
| 卡块计数口径混乱（197 卡、198 块） | 多摄入标题块或漏卡 | 以 `canonical_entities.json` 为准逐卡核对，不以分隔符数量代替卡数 |
| 模型别名漂移 | 复现实验困难 | 同时记录请求模型名和 API 返回模型名；`luna` 返回 `terra` 作为已知别名记录 |

## 五、P1：标注准则、候选 Schema 与 Prompt

### 5.1 先写准则，后跑模型

标注准则至少明确：

1. **先修 prerequisite**：不理解 A，会实质阻断对 B 的理解或应用，才允许 A→B。
2. “有帮助但非必需”“同主题”“经常一起出现”不得判为先修。
3. **相关 related**：存在对照、易混、延伸或共同解释价值，但没有必要的先后顺序。
4. 认知层级、K 标签、S 场景只用于候选剪枝和提示，不是边成立的证据。
5. 关系证据只能引用卡文原句；外部常识、归档旧边、模型常识均不得作证据。
6. 无法确定时允许 `DEFER`，不得强行选边。
7. **配置漂移是阻断问题**：交接简报指定 Vimox Router + `gpt-5.6-luna` + `glm-embedding-3-pro`，但 `run_lightrag.py` 当前默认值仍可能是旧端点、旧模型、旧 embedding。必须在 P0 修复并用实际运行日志验收；只改注释、不改有效配置，视为未修复。

### 5.2 候选对剪枝策略

全量无序概念对为 19,306 对，不能全部送模型和人工。采用“高召回、后裁决”的三路召回：

1. **语义近邻路**：用 `glm-embedding-3-pro` 对允许字段生成向量，每卡取 Top-K 近邻。
2. **标签邻域路**：同知识标签、同场景或相邻认知层级的概念对进入候选池。标签只负责缩小搜索空间，不证明关系。
3. **跨域补漏路**：保留一小批跨标签高相似对与随机分层抽样对，用于测漏边风险。

所有概念对先按无向对去重，再由 LLM 判断方向和类型。K 值不在全量阶段拍脑袋决定，必须由 K1 全 190 对基准测得。

### 5.3 Prompt 设计

模型角色限定为“候选关系提议器”，不是裁决者。每次输入一个概念对，包含：

- 卡 A、卡 B 的规范名；
- 两卡允许字段全文；
- 关系定义与反例；
- 输出 JSON Schema；
- 禁止使用外部知识、禁止输出第三个实体、禁止改写实体名、禁止引用旧字段。

模型内部判断选项：

- `PREREQUISITE_A_TO_B`
- `PREREQUISITE_B_TO_A`
- `RELATED`
- `NO_RELATION`
- `INSUFFICIENT_EVIDENCE`

只有前 3 类进入 `proposed_edges.jsonl`；后 2 类保留在评测日志中，不进入裁决队列。

### 5.4 候选边字段设计

```json
{
  "pair_id": "1-01__1-02",
  "source": "1-01 人工智能",
  "target": "1-02 ……",
  "relation_type": "prerequisite",
  "direction": "source_to_target",
  "evidence": [
    {
      "card_id": "1-02",
      "field": "精确定义",
      "quote": "卡文逐字原句"
    }
  ],
  "proposal_reason": "只解释卡文如何支持该候选，不引入外部知识",
  "ai_confidence": 0.78,
  "evidence_grade": "B",
  "candidate_sources": ["semantic_topk", "same_tag"],
  "model_requested": "gpt-5.6-luna",
  "model_returned": "gpt-5.6-terra",
  "prompt_version": "edge-proposal-v1",
  "status": "PROPOSED_UNVERIFIED"
}
```

`ai_confidence` 只用于排序，不是可信度证明，不得设置“高于某分自动通过”。建议同时保留：

- `evidence_grade`：A=双卡均有直接原句；B=一张卡有直接原句、另一张提供定义支撑；C=证据弱，只能排队候审。
- `direction_margin`：模型对两个方向的相对把握，仅用于发现方向不稳的概念对。

### 5.5 产出物

- `annotation_guidelines.md`
- `proposed_edge.schema.json`
- `edge_proposal_prompt.md`
- `candidate_pair_strategy.md`
- `prompt_test_cases.jsonl`：正例、反例、相关、无关系、证据不足、实体名诱导等测试集。

### 5.6 验收标准

- 准则覆盖先修、相关、无关系、证据不足和方向冲突五类情况。
- Schema 能拒绝非法实体名、非法关系类型、空证据和非规范状态。
- Prompt 测试中不得产出第三方实体或规范表外实体。
- 所有 `evidence.quote` 必须能在指定卡和指定字段中做逐字子串匹配。
- 所有候选边状态固定为 `PROPOSED_UNVERIFIED`。

### 5.7 风险点

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 语义相似被误判为先修 | 伪依赖大量涌入 | Prompt 写明“相关≠先修”；分开评分；人工四选一 |
| 认知层级被当成方向真理 | 产生机械倒推关系 | 层级仅用于召回；边必须由卡文证据支持 |
| 模型伪造引文 | 候选不可审计 | 逐字子串校验，校验失败直接丢弃并记录 |
| 置信度造成自动通过幻觉 | 未核验边偷渡 | 明令禁止阈值自动采纳；只用于排序 |

## 六、P2–P3：K1 小样端到端验证

### 6.1 为什么 K1 要做全 190 对裁决

20 卡只有 190 个无序概念对，规模可控。仅裁决 AI 提议出来的候选，无法知道模型漏掉了什么；因此 K1 应对 190 对做一次完整人工判断，建立小样金标准。它用于测：

1. 剪枝召回率；
2. 候选类型与方向准确率；
3. Prompt 的证据可靠性；
4. 全量阶段应取多大的 Top-K 和阈值。

### 6.2 K1 执行顺序

1. 按固定配置重新摄入 K1 20 卡，确认 20 个规范实体。
2. 建立 190 对全量清单。
3. 用三路召回生成候选池，再由 luna 生成候选关系和证据。
4. 主裁决人对 190 对进行盲裁决；界面不显示归档旧边，默认也不显示 AI 建议。
5. 完成首轮判断后，才揭示 AI 建议，用于统计一致/不一致，不允许反向修改原始裁决记录。
6. 基于 K1 金标准调 Top-K、Prompt 和队列排序。
7. 单独测试向量检索质量。

### 6.3 K1 产出物

- `k1_all_pairs.jsonl`：190 个概念对。
- `k1_proposed_edges.jsonl`：AI 候选，全部未核验。
- `k1_gold_decisions.jsonl`：人工全量裁决结果。
- `k1_proposal_metrics.json`：候选召回、精度、方向准确率、证据通过率。
- `k1_retrieval_benchmark.jsonl`：检索测试问题、期望卡、实际 Top-K。
- `k1_validation_report.md`：是否允许进入全量阶段的明确结论。

### 6.4 K1 硬验收标准

**实体与格式**

- 规范实体命中率 100%；表外实体数 0；实体变体数 0。
- JSON Schema 通过率 100%。
- 证据逐字可回查率 100%；伪造引文数 0。
- 候选边状态合规率 100%，不得出现自动接受状态。

**候选质量**

- 对人工确认的先修直连边，候选池召回率目标 ≥90%。
- 先修方向准确率目标 ≥85%。
- 若召回未达标，必须扩大候选池或调整 Prompt，不能靠降低验收口径过关。
- `related` 与 `prerequisite` 混淆率应单列；不得合并成一个“关系正确率”。

**检索质量**

- 建立不少于 20 条 K1 测试问题，覆盖名称检索、定义检索、误解辨析、案例检索。
- Recall@5 ≥90%；MRR 单列报告；不得出现空结果或表外实体。
- 检索评测只证明“找卡能力”，不证明“边正确”。

**运行稳定性**

- 相同输入重复运行两次，实体集合必须完全一致。
- 候选数量可波动，但新增/消失候选及原因必须可追踪到模型和 Prompt 版本。

### 6.5 K1 风险点

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 只检查候选精度，不检查漏边 | 全量剪枝把真边剪掉 | K1 对 190 对全量裁决，以金标准测召回 |
| 裁决者先看到 AI 答案 | 锚定污染 | 先盲裁决，后揭示 AI 建议 |
| 样本只来自 K1，跨标签关系未覆盖 | 全量阶段跨域漏边 | P5 增加跨标签高相似与分层抽检通道 |
| 检索指标被拿来替代图谱指标 | “能搜到”被误称“边正确” | 检索和建边分别出报告、分别验收 |

## 七、P4：人工裁决流程定版

### 7.1 裁决界面

推荐本地裁决页，但不能只做一个会丢数据的静态页面。至少具备：

- 左右并排显示两张卡的可信字段；
- 首轮盲裁决时隐藏 AI 建议和分数；
- 选项：A→B 先修、B→A 先修、相关、无关系、暂缓；
- 显示候选证据原句，并可定位到卡和字段；
- 自动保存、断点续作、撤销上一条；
- 防止同一概念对重复裁决；
- 导出 JSONL/CSV；
- 显示已完成数、暂缓数、剩余数，不显示诱导性的“推荐答案”。

### 7.2 裁决记录格式

每条记录必须包含：

- `pair_id`
- `decision`
- `source` / `target` / `relation_type`
- `evidence[]`
- `adjudicator`
- `adjudicated_at`
- `guideline_version`
- `candidate_id`
- `ai_agreement`
- `notes`
- `status`

`status` 只能是：`ACCEPTED_HUMAN`、`RELATED_HUMAN`、`REJECTED_HUMAN`、`DEFERRED`。

### 7.3 批次策略

- 每批 40–60 对，控制连续判断疲劳。
- 每批结束立即导出快照和校验报告。
- 下一批开始前处理上一批新增环和方向冲突。
- 暂缓项集中到最后复核，不在主流程中反复打断。
- 主裁决人保持单一；若引入第二人，仅处理暂缓与争议项，并保留仲裁记录。

### 7.4 推断与冲突处理

1. 基础可信边集只保存人工确认的**直连先修边**。
2. 传递闭包单独生成 `derived_edges.jsonl`，状态为 `DERIVED_TRANSITIVE`。
3. 已有 A→B、B→C 时，A→C 可用于“无需再问”的队列消重，但不伪装成人工直连边。

## 十一、未来增量升级方案：新增“物理AI”节点

### 11.1 结论

**已考虑扩展，但必须采用“基线冻结 + 增量包 + 局部重建 + 全图回归”的方式。**

新增一个“物理AI”节点，不需要把旧图推倒重做，也不能直接把新节点塞进正式图后让 LightRAG 自己猜边。正确结果应是：

```text
已验收基线 G_v1
  + 新节点卡 N_new
  + 新节点与旧节点的候选关系
  + 人工裁决后的新增可信边
  + 受影响拓扑/CIS/检索的局部更新
  + 全图一致性回归
= 新版本 G_v2
```

旧版本 `G_v1` 必须保留不动；新版本通过验收后，只切换发布指针。这样失败时可以立即回滚，不需要从头重建。

### 11.2 增量升级的适用边界

| 变化类型 | 是否需要重跑旧节点全部两两组合 | 处理方式 |
|---|---:|---|
| 新增一张完整概念卡“物理AI” | **不需要** | 生成新卡与旧卡的候选对，人工裁决新增边 |
| 新增多张概念卡 | **不需要** | 新卡与旧卡、新卡之间生成候选对；按批裁决 |
| 修改新卡内容但尚未发布 | **不需要** | 删除该卡未发布候选，按新内容重生成 |
| 修改旧卡定义/误解/案例 | **需要局部重评估** | 重评估该旧卡相关的全部边，并检查其祖先/后继影响 |
| 修改先修判定准则 | **原则上需要重评估全图** | 旧边的判定依据已变化，不能只补新边 |
| 只改可视化或检索参数 | **不需要** | 重新构建表现层并跑回归 |
| 更换 embedding 模型 | **不需要重裁决旧边，但需要重建向量索引** | 旧边不变；候选召回和检索指标必须重新验收 |

### 11.3 “物理AI”新增节点的具体流程

#### A. 新卡入库前

1. 为“物理AI”分配**永久唯一卡号**，不得复用旧卡号；卡号规则由节点注册表决定，不由模型生成。
2. 完整填写可信卡文：中文名、知识标签、学习场景、认知层级、精确定义、常见误解、典型案例、反例、深度上限、安全与伦理边界、来源依据、教学类比。
3. 生成新卡自己的 `card_id`、规范名、内容哈希和版本号。
4. 做名称冲突、概念重叠和卡文完整性检查。若“物理AI”只是旧卡的别名或子主题，先判定是新增节点还是旧卡修订，不能重复建点。
5. 新卡不得携带或恢复旧版“前置/后续”字段；这些字段仍然视为不存在。

#### B. 生成增量候选边

若当前基线有 `N_base` 个节点，新增一个节点后，新增无序概念对上限是：

```text
N_base 条新卡-旧卡对
```

如果同时新增 M 张卡，则候选对上限是：

```text
M × N_base + M × (M - 1) / 2
```

实际发送给模型的数量仍由 K1 验证过的三路召回策略控制：

1. 对“物理AI”生成 embedding，并与所有旧卡做近邻召回；
2. 按知识标签、学习场景、认知层级召回候选；
3. 增加跨标签补漏和人工指定候选，防止“物理AI”这种跨域概念被标签剪枝误杀；
4. 只对新增候选调用 `gpt-5.6-luna`；
5. 每条候选继续引用新卡或旧卡的卡文原句，状态固定为 `PROPOSED_UNVERIFIED`。

**不得因为增加一个节点就重跑旧节点之间的全部 19,306 对组合。** 只有旧卡内容、判定准则或召回模型发生变化时，才触发相应范围的重评估。

#### C. 人工裁决新增关系

1. 将“物理AI”与旧卡的候选对放入独立增量批次，例如 `delta-物理AI-001`。
2. 首轮裁决继续盲于 AI 建议，只显示两张卡的可信内容和证据。
3. 裁决结果只能是：A→B 先修、B→A 先修、相关、无关系、暂缓。
4. 对接受的新增先修边，检查是否形成环；若新增边与旧 DAG 冲突，必须暂缓并复核，不能强行删旧边迁就新卡。
5. 新增相关边写入相关层，不参加拓扑排序。
6. 传递关系单独生成，不能把“物理AI 可由 A→B 推出”伪装成“主公已经人工确认 A→物理AI→B”。

#### D. 增量合并与局部重建

新增边人工通过后，生成独立增量包：

- `delta_manifest.json`
- `new_cards.jsonl`
- `delta_proposed_edges.jsonl`
- `delta_decisions.jsonl`
- `delta_accepted_prerequisite_edges.jsonl`
- `delta_accepted_related_edges.jsonl`
- `delta_derived_edges.jsonl`
- `delta_validation_report.md`

合并顺序固定为：

1. 复制 `G_v1` 为候选工作区，不在生产 workdir 原地修改；
2. 加入“物理AI”节点及内容索引；
3. 只加入 `ACCEPTED_HUMAN` 的新增直连边和 `RELATED_HUMAN` 的新增相关边；
4. 重新计算受影响节点的拓扑层和 CIS；
5. 对全图重新跑节点、边、环、证据、状态和计数校验；
6. 在独立 workdir 完成 LightRAG 增量摄入或从基线快照重建；
7. 生成 `G_v2` 全套图谱产物；
8. 全部验收通过后，发布指针从 `G_v1` 切换到 `G_v2`。

### 11.4 增量影响分析

新增一个先修节点或新增一条先修边，可能改变的不只是它自己：

- “物理AI”的后继节点及其所有下游节点的拓扑层可能变化；
- “物理AI”的祖先节点的 CIS 可能增加；
- 新卡可能改变相关图的局部密度和可视化布局；
- 新卡加入向量索引后，旧查询的 Top-K 结果可能发生变化。

因此采用“两层计算”：

1. **局部计算**：对新增节点、其直接邻居、可达祖先、可达后继重新计算影响指标，作为增量报告。
2. **全图校验**：对全量节点和边重跑最终断言，确保没有旧环、重复边、状态污染、计数不一致。

局部计算用于节省成本；全图校验用于保证发布安全。只做局部校验不允许发布。

### 11.5 增量版本与回滚

每次图谱发布必须有不可变版本：

- 基线：`graph-v1.0.0`
- 新增“物理AI”且仅增加节点与边：`graph-v1.1.0`
- 修订旧卡定义或重新裁决旧边：`graph-v2.0.0`
- 仅修复展示或构建错误：`graph-v1.1.1`

版本包至少记录：

- `base_graph_version`
- `delta_id`
- 新增/修改/废弃节点清单
- 新增/修改/废弃边清单
- 输入文件哈希
- 模型、embedding、Prompt、准则版本
- 变更前后节点数、边数、拓扑层数、孤立节点数、CIS 变化
- 验收报告和回滚目标

回滚只做发布指针切换到上一个已验收版本，不删除任何历史包，不在生产目录执行破坏性覆盖。

### 11.6 增量升级验收标准

“物理AI”版本必须同时满足：

1. 基线图 `G_v1` 文件哈希保持不变。
2. 新节点规范名唯一，实体注册表只增加该节点，不修改旧节点身份。
3. 新增候选边 100% 带卡文证据，全部未裁决候选仍为 `PROPOSED_UNVERIFIED`。
4. 正式新增先修边 100% 有人工裁决 provenance。
5. 新增先修边不产生自引用、重复边、双向边或 SCC。
6. 旧的人工确认边数量、方向、类型和 provenance 零变化，除非本次明确批准旧边修订。
7. 新旧图合并后节点数为 `N_base + 1`；若基线确为 197，则必须是 198；若基线确为 192，则必须是 193。
8. 新旧图合并后全图拓扑排序成功；孤立节点变化有解释。
9. 受影响节点的拓扑层、CIS、入度、出度变化有增量报告。
10. 原有 K1 检索回归集 Recall@5 不低于基线；新增“物理AI”相关测试问题达到同一验收口径。
11. LightRAG、`trusted_edges.jsonl`、`graph.json`、GraphML、HTML 的节点与边计数一致。
12. 旧版本可通过发布指针一键回滚。

### 11.7 增量升级的风险点

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 把新增卡直接写进旧生产图 | 无法回滚，旧图被污染 | 基线只读；复制到候选工作区；通过版本指针发布 |
| 只给新卡找相似卡，不做人工指定补漏 | 跨域先修关系被剪掉 | embedding + 标签 + 跨域补漏 + 人工指定候选四路合并 |
| 新增边造成旧 DAG 环 | 学习路径和拓扑失效 | 每条增量边后跑 SCC；冲突时暂缓，不删旧边 |
| 新卡内容改变但旧边不复核 | 旧关系证据失效 | 旧卡内容变更触发相关边局部重评估 |
| 传递边数量暴涨 | 把推断误当人工事实 | 传递边独立图层、独立状态、默认不进入基础边集 |
| 新节点改变旧查询 Top-K | 检索回归下降 | 固定回归集；发布前比较新增前后 Recall@5、MRR 和答案实体 |
| 192/197 基线口径混乱 | 节点计数和版本判断错误 | 以 `source_manifest.json` 为唯一准数；口径不一致时阻断发布 |

### 11.8 可复用的增量升级模板

未来新增任意节点，统一套用以下模板：

```text
1. 核定当前发布版本和基线节点数
2. 编写并校验新卡，分配永久唯一卡号
3. 生成新卡内容哈希和 delta_manifest
4. 只召回“新卡 × 旧卡”及“新卡 × 新卡”候选对
5. 生成 AI 候选边，全部标 PROPOSED_UNVERIFIED
6. 人工盲裁决，记录 provenance
7. 检查新增 DAG、局部影响和传递关系
8. 在基线副本上合并新增节点与可信边
9. 重建/增量更新索引，跑全图一致性回归
10. 生成新版本并切换发布指针
11. 保留旧版本，可一键回滚
```

**最终结论：未来扩展可行，而且不需要推倒重来；但扩展的最小单位不是“加一张卡”，而是“新卡 + 候选关系 + 人工裁决记录 + 增量验证报告 + 可回滚版本包”。**

## 十二、成本与执行控制

1. **模型不升级**：候选提议固定使用 `gpt-5.6-luna`；只有 K1 指标不达标且有对照实验时，才能提出升级。
2. **单对幂等缓存**：`pair_id + prompt_version + model_returned` 作为缓存键，避免失败重跑重复计费。
3. **两段式调用**：先用 embedding 召回概念对，再让 luna 做关系提议；不把 19,306 对全部送入 LLM。
4. **增量落盘**：每处理一个概念对就写 JSONL，支持断点续跑。
5. **预算闸门**：K1 完成后，根据“每有效候选成本、每人工接受边成本、召回曲线”估算全量费用，再启动 P5。
6. **全量执行编排**：日常批处理、校验和重试由 glm5.3flash 负责；准则修订、争议裁决和质量复盘使用 gpt-5.6-sol。

## 十三、推荐执行顺序

1. 先修 `run_lightrag.py` 的实际默认配置漂移，并生成 P0 五份基线文件。
2. 编写 `annotation_guidelines.md`、候选 Schema 和 Prompt 测试集。
3. 对 K1 20 卡建立 190 对全量裁决基准，测出真实召回率。
4. 依据 K1 数据定剪枝 Top-K 和全量阈值，不凭感觉拍数。
5. 定版裁决页和裁决记录格式。
6. 生成全量候选并分批人工裁决，每批都跑 DAG 校验。
7. 只把人工通过的边合并进 LightRAG。
8. 输出 JSON、GraphML、HTML、拓扑分层与完整审计报告。

**最终可用性判定：**

- P0–P5 产出的只是节点、候选和流程资产，**不能作为正式学习依赖图使用**。
- P6 完成后，人工确认的直连边开始具备正式使用资格。
- P7–P8 全绿后，整套图谱才可用于学习路径、课程编排和正式展示。
